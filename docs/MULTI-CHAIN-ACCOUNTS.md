# Multi-chain accounts (design note)

Status: proposal, not built. Licence: CC BY 4.0.

## What

bBots that trade need accounts on other chains: BTC, SOL and ETH (and maybe
more later). Each is a separate account inside bWalletX, shown next to the BSV
accounts, used mainly to swap into BSV.

## The licence rule

bWalletX's own code is under the Open BSV License, which only allows use with
the BSV blockchain. `@bsv/sdk` and the other `@bsv/*` packages are under the same
licence. So the BTC/SOL/ETH code must not use any of it:

- Use each chain's own MIT/Apache libraries (for example `@scure/btc-signer`
  or `bitcoinjs-lib` for BTC, `@solana/web3.js` for SOL, `viem` for ETH, and
  `@scure/bip32`/`@scure/bip39`/`@noble/*` for keys and crypto).
- Never import `@bsv/*`, `@1sat/*`, or any bWalletX file under the Open BSV
  License from that code.
- The multi-chain code itself is published under MIT (or Apache-2.0), not
  Open BSV, so it can legally touch other chains.

## Clean boundary

- Lives in its own package, e.g. `packages/multichain/` with its own
  `package.json` and `LICENSE` (MIT). Nothing else lives there.
- An ESLint `no-restricted-imports` rule for that folder bans `@bsv/*`,
  `@1sat/*` and relative imports out of the package.
- A test (`bun test`) walks the package's import graph and its
  `package.json` dependencies and fails if any `@bsv/*` package shows up,
  directly or transitively.
- The wallet talks to it through a small typed interface (get address,
  balance, sign and send, quote swap). Data crosses the boundary, code does not.

## Keys

- Derived separately from the BSV keys: own BIP-32/BIP-44 paths per chain
  (BTC m/84'/0', ETH m/44'/60', SOL m/44'/501'), derived by the multichain
  package's own libraries, not by `@bsv/sdk`.
- Open question below on whether they share the user's seed or get their own.
- Bot accounts have spending limits and can be switched off per bot.

## Main flow: swap into BSV

1. bBot (or user) holds BTC/SOL/ETH in its account.
2. Swap via a swap provider (ChangeNOW-style) into a BSV address of the same
   user, generated by the normal BSV side of the wallet.
3. Funds land as BSV; everything else in bWalletX carries on as today.

## Open questions for the owner

1. Same seed as BSV (one backup) or a separate seed (cleaner licence and risk
   split)? Recommendation: same seed, different paths, but derived only by the
   MIT package.
2. Which chains first? Recommendation: BTC, then ETH, then SOL.
3. Which swap provider, and do we take a fee?
4. Are bot accounts custodial anywhere (server-side bots) or always on the
   user's device? Locks-non-custodial rule suggests device or user-held keys only.
5. Should we get a lawyer to confirm the Open BSV boundary (and patents)
   before shipping?
